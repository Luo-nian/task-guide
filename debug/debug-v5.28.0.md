## C-031 · 追踪名额"假满"：解锁完整版、上限 3，却只能追 1 个（定案）

- 现象（boss 亲测报障）：已解锁完整版、设置追踪上限 3，追踪第 2 个任务仍被拦截。
- 真机 DB 实证（v5.28.0 装机后拉库快照）：
  `track_status='tracking'` 共 **5 行**，其中 **4 行 `deleted=1`**（v5.21 引入上限之前的
  历史追踪任务，被软删除但状态位没清）+ 仅 1 行活任务。
- 根因：拦截用的计数口径**没有排 `deleted`** → 数出 5 ≥ 上限 3 → 误拦。
  软删除模型下「删除 ≠ 状态清理」，**配额/计数类 SQL 必须与列表口径同步带 `deleted = 0`**。
- 修复（已在位，无需再改码）：v5.27.1（bbe41b9）`Database.kt` 的
  `countTracking` / `observeTrackingCount` 均已带 `AND deleted = 0`；
  调用链 `TaskRepository:365 → taskDao.countTracking()` 唯一，无旁路口径。
- 真机复验：装机 v5.28.0 后计数 = 1（正确口径），主页「正在追踪 1」与 DB 一致，
  上限 3 → 现可正常追 2 个新任务。4 条死占坑行无害（不再计入），不强改库。
- ⭐ 教训：透明化（toast 显示 N/M）只是止痛；计数口径对齐活行才是根治。
  同类风险点：任何 `COUNT(*)` 用于配额/上限判断的 SQL，都要 grep 一遍有没有 `deleted` 过滤。

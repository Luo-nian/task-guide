## C-017 ⭐「喝水 8 次」字体为什么不一样 —— 已解决（M1）

**boss 原话**：为什么主页的喝水8次的任务的字体不一样？

**真因**：两层"不同"叠加 ——
1. 「喝水 8 次」是 `type=once` 的普通任务（走 **TaskRow**），旁边的习惯走 **HabitRow**；
2. 更隐蔽的是 **TaskRow 自己内部还有两条渲染路径**：
   - 一条：紫色小菱形 + 标题 `17sp Medium`
   - 另一条（带分类/优先级 chips + 时钟）：标题 `16sp SemiBold`

于是同一个列表里字号 + 字重都在跳。

**修法**：统一为 `17sp Medium`（与 HabitRow / 追踪布局对齐）。

> 教训：**"同一个组件"不等于"同一种样式"** —— TaskRow 有一百多行，内部按状态分了多套布局，
> 改样式/查不一致时要**通读组件内部所有分支**，不能只看函数签名。

## C-018 ⭐ 深色卡片上用了深色文字 —— 已解决（P5）

**症状**：电脑端身份卡的「晚上好，boss」在深色卡上**几乎看不见**（截图里是暗灰色）。

**真因**：`.dash-greet-text` 的 `color: var(--ink)` —— `--ink` 是**给浅色底用的深色文字**。
身份卡是深色底 → 深色字画深色底 → 对比度接近 0。

**修法**：改用亮金色 `--gold-light` + 一层轻阴影；**下一行的等级名/积分不动**（它们本来就清晰）。

> 通用检查：**深色容器里绝不能沿用浅色系的 `--ink`**。做深浅两套面板时，文字色必须跟着容器走。

## C-019 ⭐ CSS 动画"扩开又缩回去"看起来就是闪烁 —— 已解决（P3）

**症状（boss）**：点追踪/取消追踪键时"会有闪烁之类的"；"那个小菱形的 菱形涟漪不太明显…
只要一个涟漪就行…现在的不像是涟漪"。

**真因**：`@keyframes rippleBreath` 是
`0%` 贴边 → `35%` 扩到 8px → `70%` **缩回 1.5px** → `100%` 静止。
即"**涨—缩—停**"循环，视觉上是**呼吸/跳动**，不是"一圈涟漪荡开"。

**修法**：改成**单向**——
```css
@keyframes rippleBreath {
  0%   { box-shadow: 0 0 0 1.5px var(--gold-light), 0 0 0 0 rgba(232,203,127,.55), 0 0 6px var(--glow-azure); }
  100% { box-shadow: 0 0 0 1.5px var(--gold-light), 0 0 0 9px rgba(232,203,127,0), 0 0 6px var(--glow-azure); }
}
```
菱形本体金边全程恒定（始终看得清），只有外面那一圈在扩散淡出。

**与手机端同步**：手机端 v5.15.26 M5 同样处理 —— 去掉**常驻内圈**（它更像"一圈静止的线"），
只留一圈从图标处荡开、边扩边变细变淡。

> 通用规则：**涟漪 = 单向扩散 + 淡出**。任何"先扩后缩"的写法都会被看成呼吸/闪烁。

## C-020 P8 实施坑：`zoom` 会让 `innerWidth` 反过来变小 —— 已规避

挂件要做"窗口变大 → 内容（含文字按钮）跟着变大"，用 `zoom` 实现。
但设了 `zoom = s` 之后，`window.innerWidth` 反映的是**缩放后**的可视宽度（变小了），
若直接拿它算 `s = innerWidth / 360`，下一次 resize 算出的 `s` 又不同 → **来回震荡**。

**规避**：用当前缩放比反算真实宽度 → `realW = window.innerWidth * cur`，再加 0.004 的容差。

- 窗口上下限写在 `tauri.conf.json`：240×180 ~ 760×1000（`resizable: true`）
- 内容缩放限制 0.8×~1.8×（缩太小看不清、放太大溢出）

## C-021 ⭐ 界面右上角弹「render err」红条 —— 已解决

**症状（boss 截图）**：电脑端界面上出现深色调试条 `[render err] _cg is not defined points=1540 level=星辰霸主`，
同时仪表盘数据全空（今日进度 0/0、近 7 日完成 0 项）。

**根因**：P4 的辅助函数（`_collapsedGroups` / `_cg` / `toggleCatGroup`）被我**插进了 `renderSideNav()` 函数内部**，
成了**局部作用域**；而调用它的 `renderTodayView()` 是**顶层函数** → `ReferenceError: _cg is not defined`
→ render 抛异常中断 → 整页渲染不出来。

**修法**：把这段整体移到**顶层**（`renderSideNav` 之前）。

> 教训：**插代码前先确认插入点所在的作用域**。```
> function renderSideNav() {        ← 我插在了这里（局部）
>   ...
>   document.querySelectorAll('.nav-item')...
> }
> ```
> 我当时的锚点是 `document.querySelectorAll('.nav-item').forEach(...)`，看着"像是顶层"，
> 其实它是 **renderSideNav 的最后一句话**。→ **锚点前必须往上多读十几行确认它属于谁**。

## C-022 ⭐⭐ Tauri 增量编译不会重新 embed 前端资源 —— 已解决（本版最大坑）

**症状**：P8（挂件鼠标缩放）改完了 `widget.html`，也编译了、也部署了新 exe，
但**挂件运行时仍是旧的**（CDP 里查 `outerHTML` 找不到新脚本）；强制 `Page.reload({ignoreCache:true})` 也无效。

**根因**：Tauri 把 `frontendDist`（ui/）的资源在 **build.rs 阶段**扫描并 embed 进 binary。
当**只改 `ui/` 下的前端文件、完全没碰 Rust 代码**时，cargo 判定 workspace 无变化 →
**build script 不重跑** → 资源停在**上一次真正编译 Rust 时的快照**。

本例中：P4 的 app3.js 改动赶上了那次全量编译（所以 P4 生效），
而 P8 的 widget.html 是在那次编译**之后**才写的 → 一直进不去。

**修法**：改完 ui/ 之后，编译前先 `touch build.rs`（或任意 Rust 源文件）强制 build script 重跑：
```bash
touch /d/taskbuild2/desktop-src/build.rs && cargo build --release --offline
```

> ⚠️ **这条要写进流程**：以后凡是"只改前端（ui/*.js|html|css）"的桌面端改动，
> **必须 touch build.rs 再编译**，否则可能出现"编译成功、exe 换了、但界面没变"。

### C-022 续：真正让挂件"死活不更新"的是 **WebView2 缓存**（第二层）

`touch build.rs` 之后仍然不生效。用 CDP 直接向资源协议取证：

```js
fetch('widget.html').then(r=>r.text()).then(t=>t.includes('BASE_W'))   // → true（资源其实是新的！）
```

**资源是新的**，但挂件页面加载到的还是旧内容 —— 说明卡在**缓存**上。

**为什么主窗口没事、只有挂件不更新**：
- 主窗口走 `index.html`，而它内部的引用是**带版本戳**的：`app3.js?v=v68`、`style.css?v=v69`
  → 我每次改前端都会把版本号推进一档 → URL 变了 → 缓存自然未命中（这就是 P4/P5 能生效的原因）
- **挂件窗口是 Tauri 直接加载 `widget.html`，URL 里没有任何版本参数** → 改了内容 URL 却没变 → WebView2 一直吃旧缓存
  （连 CDP 的 `Page.reload({ignoreCache:true})` 都冲不掉）

**最终修法**：把版本戳补到窗口 URL 上 ——
```json
{ "label": "widget", "url": "widget.html?v=26", ... }
```
以后每次改 `widget.html`，**把这个版本号 +1** 即可。」

**顺带得到的通用规则**：
> **任何被"按 URL 缓存"的资源，改内容时都必须同时改 URL**。
> 主窗口文件靠 `?v=` 做到了；挂件窗口漏了 → 补上。
> 判断缓存问题的最快方法：**用 `fetch()` 直接取资源看内容**，它和"页面实际渲染的"对比就能立刻分清
> 是"资源没更新"还是"缓存没刷新" —— 这两种情况的修法完全不同。
> 判断方法：改一个**肉眼可见**的标记（如文案），编译部署后看是否出现 —— 不出现就是没 embed。

## 一、boss 亲测 bug：追踪上限失效 —— 排查结论 🟡

### 排查过程（全链路）

| 环节 | 文件:行为 | 结论 |
| --- | --- | --- |
| UI 拦截点 | `Screens.kt:517/986` 两处 `vm.startTracking(uuid){ok->}` | ✅ 只是 toast，判定在下游 |
| VM 层 | `TaskViewModel.startTracking` → `repo.startTracking` 直通 | ✅ 无 gate |
| 仓库层 | `TaskRepository.startTracking:364-366`：`limit=getTrackLimit(); if(countTracking()>=limit) return false` | ✅ 逻辑正确 |
| 上限读取 | `getTrackLimit()` = settings 表 `track_limit` 键，缺省 3 | ✅ v5.21~v5.27 全版本一致 |
| Pro 判定 | `License.isPro` = prefs 里 `PREF_CODE` 验签；VM combine：pro→设置值，非 pro→1 | ✅ 设置页能显示 3 说明 pro=true |
| **唯一嫌疑** | **数据层：DB 里 `track_status='tracking' AND deleted=0` 的行 ≥3，但界面上 boss 只认得 1 个** | 🟡 最可能 |

### 为什么会有"看不见的追踪名额"

- v5.21.0 之前**没有追踪上限**，追过的任务永远 `tracking`（除非手动取消）
- 主页把 tracking 任务抽到**置顶区**显示（`Screens.kt:265-290`），普通列表里**看不到它们**——
  boss 对"我正在追踪什么"的感知 ≈ 最近点过的那 1 个，历史占坑的他不知道
- 还有一个待排除的污染源：**桌面端全量推送回灌旧 track_status**（v5.15.22 C-001 修过 HTTP 层，
  但若桌面 DB 里存着 v5.18 时代的旧 tracking 行，每次 push_full 都可能把手机端的取消操作覆盖回去）

### 本轮已落地的修复（v5.27.1，编译通过 ✅）

1. **拦截 toast 显示实况**：两处（TaskRow/HabitRow）改为
   「追踪名额已满(3/3)，先取消别的追踪或在设置里调高上限」——一被拦立刻知道占用了几个
2. **设置页上限卡片加实况行**：「正在追踪 N 个」；
   满=红色并提示「名额已满，回主页置顶区可取消」
3. 新增 `TaskDao.observeTrackingCount()` / `repo.observeTrackingCount()` / `vm.trackingCount`

### 待 boss 手机连上后验证（一次搞定）

1. 装 v5.27.1 → 设置页看「正在追踪 N 个」：
   - N≥3 且置顶区确实有 N 个 → **不是 bug，是老任务占坑** → 在置顶区取消即可（若想清空：逐个取消）
   - N<3 还被拦 → 把 toast 数字记下来报我（那就是更深的数据问题）
2. 顺手验证：主页置顶区把所有 tracking 任务数一遍 = 设置页的 N

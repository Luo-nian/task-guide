# 安全审计与加固方案

> 审计日期：2026-09-19
> 审计范围：桌面端（Tauri2 / Rust 2642 行 + 前端 11456 行）、手机端（Kotlin 10393 行）
> 审计目标：① 会不会被入侵/篡改为病毒 ② 会员代码会不会被简单破解 ③ 上线前的加密保护
> 结论：**发现 4 个真实漏洞，其中 2 个为 P0（上线前必须修）**

---

## 一、审计发现

### 🔴 P0-1 · 手机端 API 完全没有鉴权，且监听 0.0.0.0

**位置**：`mobile/.../server/SyncService.kt:90`

```kotlin
val eng = embeddedServer(CIO, host = "0.0.0.0", port = port) { ... }
```

**证据**：`ApiRoutes.kt` 里只安装了 `WebSockets` 与 `ContentNegotiation` 两个插件，
**没有任何认证插件 / 拦截器 / Token 校验**。

**暴露的接口（全部无需凭证即可访问）**：

| 接口 | 危害 |
| --- | --- |
| `GET /api/sync/full` | **读取用户全部任务、习惯、设置**（隐私泄露） |
| `POST /api/sync/changes` | **写入 / 删除用户数据**（数据被毁） |
| `POST /api/settings/upsert` | **篡改用户设置** |
| `POST /api/pair` · `/api/pair/clear` | **任意配对 / 解除配对** |
| `GET /api/sync/incremental` | 增量数据泄露 |

**攻击场景**：用户在咖啡馆 / 学校 / 公司 WiFi 下打开 App →
同网段任意设备 `curl http://<手机IP>:8899/api/sync/full` 即可**拿走全部数据**；
`POST /api/sync/changes` 即可**清空或篡改**。

### 🔴 P0-2 · 配对机制形同虚设（不校验配对码）

**位置**：`ApiRoutes.kt:60`

```kotlin
post("/api/pair") {
    val name = ...            // 直接取请求里的名字
    app.repo.setSetting("paired_device", name)   // 直接写入，无任何校验
    ...
}
```

**证据**：全项目搜索 `配对码 / pairCode / pin`，**没有任何校验逻辑**。
（boss 早前收到过「配对码 767022」，但代码里从未使用它。）

**后果**：配对不是安全边界 —— 任何人都能配对成功，P0-1 的接口也就等于全开。

### 🟠 P1-1 · 明文传输（ws:// / http://，无 TLS）

**位置**：`desktop/src/sync.rs:506`

```rust
let ws_url = base.replace("http://", "ws://") + "/ws";
```

同一局域网内可被**嗅探**（任务内容、设置全部明文）。
注：局域网自签证书体验差，**建议用「共享密钥 + HMAC 签名」替代 TLS**（见加固方案）。

### 🟠 P1-2 · 数据明文存储

**证据**：桌面端与手机端均为**普通 SQLite**，无 SQLCipher / 字段加密。
**后果**：桌面端 `taskguide.db` 文件可直接用任何 SQLite 工具打开读取；
手机端在有 root 或通过备份导出时同样可读。
**评估**：属于「本地数据保护」范畴，优先级低于 P0，但对隐私承诺有影响。

### 🟢 桌面端的良好实践（无需修）

- 单实例锁**只绑 `127.0.0.1:53911`**，不对外暴露 ✓
- 未发现桌面端对外监听端口 ✓

## 二、加固方案

### 2.1 身份与鉴权（解决 P0-1 + P0-2）

**设计：一次性配对码 → 长期共享密钥**

```
① 手机端生成 6 位随机配对码（有效期 5 分钟，仅屏幕显示）
② 用户在桌面端输入该码 → 桌面端把码发给手机端 /api/pair
③ 手机端校验码（含有效期 + 尝试次数限制）
④ 校验通过 → 手机端生成 <32字节随机 secret> 返回给桌面端
⑤ 双方把 secret 持久化；此后所有请求带 X-TB-Token: <secret>
⑥ 手机端中间件校验：不匹配的请求一律 401
```

**要点**：
- 配对码 **5 分钟过期** + **最多尝试 5 次**（防暴力破解 6 位码）
- 未配对状态下**只放行** `/api/ping` 与 `/api/pair`
- secret 用 **常量时间比较**（防时序侧信道）
- 换设备 / 解除配对 → secret 立刻作废

### 2.2 防篡改（替代 TLS 的务实做法）

给每个请求体加 **HMAC-SHA256 签名**：

```
X-TB-Token: <secret>
X-TB-Sign:  HMAC_SHA256(secret, method + path + body + timestamp)
X-TB-Time:  <unix 秒>
```

手机端校验：**签名正确 + 时间戳在 ±300 秒内**（防重放）。
→ 攻击者即使嗅探到请求，也无法**篡改**或**重放**（因为改不动签名、且时间戳会过期）。

### 2.3 数据保护（P1）

- **桌面端**：把 `taskguide.db` 迁到用户私有目录（`%APPDATA%`）并收紧文件 ACL
- **手机端**：依赖 Android 应用沙箱（已足够）；如需更强可后续上 SQLCipher
- **敏感字段**（昵称、备注）可选做字段级加密

### 2.4 上线加固（防逆向 / 防篡改）

| 措施 | 平台 | 说明 |
| --- | --- | --- |
| **正式签名 keystore** | 手机端 | ⚠️ 当前 release **用的是 debug 签名**，必须换 |
| **R8 / ProGuard 混淆** | 手机端 | 开启后类名/方法名被混淆，显著提高破解成本 |
| **资源混淆 + 字符串加密** | 手机端 | 关键字符串（密钥、接口）不裸奔 |
| **Rust 侧 LTO + strip** | 桌面端 | 减小体积、去掉符号表 |
| **完整性自检** | 双端 | 校验自身签名/哈希，被重打包能察觉 |
| **不要在前端存密钥** | 桌面端 | 前端 JS 是明文的，密钥只放 Rust 侧 |

## 三、会员系统设计（含 boss 要求的 5 轮加固）

### 3.1 权益定义（沿用 boss 拍板 + 我补充）

| 权益 | 免费 | 会员 |
| --- | --- | --- |
| 任务数量 | 不限 | 不限 |
| **追踪任务上限** | **1 个** | 不限 |
| **导出 JSON** | ❌ | ✅ |
| **跨端同步** | ❌ | ✅ |
| **桌面挂件** | ❌ | ✅ |

> ⚠️ **架构前提**：「会员一定是服务端判定的」。
> 若只在客户端判断，用户改一下本地库就能白嫖。
> 因此会员系统与「跨端同步」共用同一个后端 —— 这也正是主卖点。

### 3.2 ⭐ 五轮加固迭代设计

| 轮次 | 做法 | 攻击者需要做什么才能破解 |
| --- | --- | --- |
| **v1** | 本地布尔值（`is_vip=true`） | 改一行数据库 |
| **v2** | 本地**签名凭证**：服务端私钥签发，客户端内置公钥验签 | 伪造签名（无解，除非拿到私钥） |
| **v3** | v2 + **设备指纹绑定**（凭证与设备 ID 绑定） | 复制凭证到别的设备无效 |
| **v4** | v3 + **时间戳 + 时钟回拨检测**（凭证有有效期） | 改系统时间会被发现 |
| **v5** | v4 + **关键功能服务端下发**（同步/导出走服务端接口，服务端按会员状态放行） | 必须攻破服务端 —— 这是最终形态 |

**v5 是终局**：只要核心权益依赖服务端，客户端怎么改都没用。

### 3.3 落地节奏（务实）

- **本次**：先把 v1–v4 的**客户端骨架 + 签名校验链路**写好（服务端可先用本地私钥模拟）
- **紧接着**：接入真实后端（Cloudflare Workers 免费额度即可）→ 升到 v5
- 后端同时承担：**跨端同步中转 + 收据校验 + 会员状态发放**

> **当前版本不能直接上架。**

# v5.17.0 加固（按 boss 指示重做配对与传输）

> boss 反馈原文：
> 「P0-1：手机端 API 完全裸奔 **所以需要双向确认**」
> 「P0-2：配对机制形同虚设 **不需要用到配对码** 只需要扫描设备 然后一端发出申请
>   另一端弹出确认窗口进行确认 **把确认之前的锁写好点**」
> 「明文传输其实没什么…你自己修吧」

## 一、配对改版：一次性配对码 → 双向确认（弹窗）

**为什么原来的做法不行**：v5.16.0 虽然加了 6 位配对码，但仍要用户手工抄一串数字，
而且**手机端不校验"是谁在申请"** —— 只要码对就发密钥，对面是谁完全不清楚。

**现在的流程**（`PairingState` / `pair_request` / `pair_poll`）：

```
电脑扫描 → 点「配对」 → POST /api/pair/request
                              ↓
手机：① 配对模式门控  ② 同 IP 限流(3/分)  ③ 单 pending  ④ kat 加密实现互校
                              ↓
手机弹确认框 →【人在手机上点「允许」】← 真正的安全边界
                              ↓
电脑 GET /api/pair/poll（仅发起方 IP，2 分钟 TTL）→ 一次性领取 master
```

### "确认之前的锁" —— 四道门（boss 明确要求）

| 门 | 做法 | 挡住什么 |
| --- | --- | --- |
| **1 配对模式门控** | 只有用户**停留在手机设置页**时才受理申请（`setArmed`） | 人没看手机时，局域网设备连申请都递不进来，更不会弹窗 |
| **2 限流** | 同一 IP 每分钟最多 3 次申请 | 暴力骚扰 / 脚本刷屏 |
| **3 单 pending** | 同一时刻只允许一个待确认申请 | 用大量申请淹没确认框、诱导误点 |
| **4 SAS 双屏核对** | 6 位数字 = sha256(cNonce‖sNonce‖sessionId) 前 6 位，**两端各自独立计算** | 中间人改过 sNonce → 两边数字对不上，用户当场发现 |

补充：sessionId 128 位随机、TTL 2 分钟、**只允许发起方 IP 轮询**、密钥**一次性交付**。

## 二、传输加密 + 双向认证（"明文传输"整改）

**为什么自己写**：编译环境是离线的（`cargo build --offline`），本地 registry 里
没有 `aes-gcm` / `ring` 可用（ring 在 Windows 上还需 nasm，本机没有）。
可用的只有 `sha2` + `base64` → 采用 **ChaCha20（流加密）+ HMAC-SHA256（认证）**：
算法极简、无平台依赖、可**逐行移植**到 Kotlin，两端各带一份 RFC 8439 自检。

| 层 | 做法 |
| --- | --- |
| **身份** | `X-TB-Token: base64(master)` |
| **新鲜度** | `X-TB-Ts`（±180s） |
| **防重放** | `X-TB-Nonce`（服务端 LRU 去重） |
| **防篡改** | `X-TB-Sig = HMAC(signKey, METHOD + PATH + TS + NONCE + sha256(body))` |
| **保密** | 请求/响应体 = `E1:` + base64(nonce12 ‖ ChaCha20(encKey, plain)) |
| **双向认证** | 请求由手机验签（证明来的是那台电脑）+ **响应由手机签名、电脑验签**（证明回话的真是那台手机） |

密钥派生：`master → HMAC(master,"tb-sign-v1") → signKey`；`→ HMAC(master,"tb-enc-v1") → encKey`。
构造上是 **encrypt-then-MAC**（对密文签名），与 AEAD 常见构造等价。

### 两处交叉验证（不是"应该能跑"）

1. **Rust 端 ChaCha20 与 RFC 8439 §2.4.2 标准向量一致**
   （用 rustc 抽取真实代码直接跑，秒级验证；顺带发现 RFC §2.4.2 的 nonce 是
   `00:00:00:00::4a::`，与 §2.3.2 块向量的 `00:00:00:09::4a::` **不同**，已用 node/OpenSSL 交叉确认）
2. **两端各带 KAT 自检**，且**配对时互校**（`kat` 字段）——版本错配会在配对那一刻
   报「两端加密实现不一致」，而不是等同步静默失败

## 三、顺手修掉的三处漏改（都会表现为"同步莫名失效"）

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | `POST /api/settings/upsert`（头像 emoji） | 加鉴权后此处**没补签名** → 手机 401，静默失败 |
| 2 | 自动重连里的"反 POST `/api/pair`" | 该接口已随配对改版删除 → 每次自动重连都打一个 404 |
| 3 | `disconnect_server` 的"通知手机解除配对" | 旧实现**先把 server_url 置空再读它**拼 base → base 永远为空，**这段从来没生效过** |

> 教训：**给接口加鉴权时，必须 grep 出全部 HTTP 调用点**，不能只改主路径。

## 四、残留风险（如实记录，未解决）

1. **配对瞬间的 master 以明文返回给发起方** —— 同网段"主动中间人"理论上可在
   这 2 分钟窗口内截获。彻底解决需 DH 密钥交换 + SAS 承诺。当前权衡：
   局域网场景 + 人工确认 + 短窗口 + 一次性交付。
2. **数据仍明文存 SQLite**（`taskguide.db` 可直接打开读）—— 需 SQLCipher，属另一个工作量级。
3. **WS 握手的 token 走查询参数**（可能落进中间设备的访问日志）。
4. **未使用传输层 TLS**（自签证书要在 WebView / Android 上各配一次信任链，收益不划算）。

# 安全审计与加固方案

> 审计日期：2026-09-19
> 审计范围：桌面端（Tauri2 / Rust 2642 行 + 前端 11456 行）、手机端（Kotlin 10393 行）
> 审计目标：① 会不会被入侵/篡改为病毒 ② 会员代码会不会被简单破解 ③ 上线前的加密保护
> 结论：**发现 4 个真实漏洞，其中 2 个为 P0（上线前必须修）**

---

## 一、审计发现

### 🔴 P0-1 · 手机端 API 完全没有鉴权，且监听 0.0.0.0

**位置**：`mobile/.../server/SyncService.kt:90`

```kotlin
val eng = embeddedServer(CIO, host = "0.0.0.0", port = port) { ... }
```

**证据**：`ApiRoutes.kt` 里只安装了 `WebSockets` 与 `ContentNegotiation` 两个插件，
**没有任何认证插件 / 拦截器 / Token 校验**。

**暴露的接口（全部无需凭证即可访问）**：

| 接口 | 危害 |
| --- | --- |
| `GET /api/sync/full` | **读取用户全部任务、习惯、设置**（隐私泄露） |
| `POST /api/sync/changes` | **写入 / 删除用户数据**（数据被毁） |
| `POST /api/settings/upsert` | **篡改用户设置** |
| `POST /api/pair` · `/api/pair/clear` | **任意配对 / 解除配对** |
| `GET /api/sync/incremental` | 增量数据泄露 |

**攻击场景**：用户在咖啡馆 / 学校 / 公司 WiFi 下打开 App →
同网段任意设备 `curl http://<手机IP>:8899/api/sync/full` 即可**拿走全部数据**；
`POST /api/sync/changes` 即可**清空或篡改**。

### 🔴 P0-2 · 配对机制形同虚设（不校验配对码）

**位置**：`ApiRoutes.kt:60`

```kotlin
post("/api/pair") {
    val name = ...            // 直接取请求里的名字
    app.repo.setSetting("paired_device", name)   // 直接写入，无任何校验
    ...
}
```

**证据**：全项目搜索 `配对码 / pairCode / pin`，**没有任何校验逻辑**。
（boss 早前收到过「配对码 767022」，但代码里从未使用它。）

**后果**：配对不是安全边界 —— 任何人都能配对成功，P0-1 的接口也就等于全开。

### 🟠 P1-1 · 明文传输（ws:// / http://，无 TLS）

**位置**：`desktop/src/sync.rs:506`

```rust
let ws_url = base.replace("http://", "ws://") + "/ws";
```

同一局域网内可被**嗅探**（任务内容、设置全部明文）。
注：局域网自签证书体验差，**建议用「共享密钥 + HMAC 签名」替代 TLS**（见加固方案）。

### 🟠 P1-2 · 数据明文存储

**证据**：桌面端与手机端均为**普通 SQLite**，无 SQLCipher / 字段加密。
**后果**：桌面端 `taskguide.db` 文件可直接用任何 SQLite 工具打开读取；
手机端在有 root 或通过备份导出时同样可读。
**评估**：属于「本地数据保护」范畴，优先级低于 P0，但对隐私承诺有影响。

### 🟢 桌面端的良好实践（无需修）

- 单实例锁**只绑 `127.0.0.1:53911`**，不对外暴露 ✓
- 未发现桌面端对外监听端口 ✓

## 二、加固方案

### 2.1 身份与鉴权（解决 P0-1 + P0-2）

**设计：一次性配对码 → 长期共享密钥**

```
① 手机端生成 6 位随机配对码（有效期 5 分钟，仅屏幕显示）
② 用户在桌面端输入该码 → 桌面端把码发给手机端 /api/pair
③ 手机端校验码（含有效期 + 尝试次数限制）
④ 校验通过 → 手机端生成 <32字节随机 secret> 返回给桌面端
⑤ 双方把 secret 持久化；此后所有请求带 X-TB-Token: <secret>
⑥ 手机端中间件校验：不匹配的请求一律 401
```

**要点**：
- 配对码 **5 分钟过期** + **最多尝试 5 次**（防暴力破解 6 位码）
- 未配对状态下**只放行** `/api/ping` 与 `/api/pair`
- secret 用 **常量时间比较**（防时序侧信道）
- 换设备 / 解除配对 → secret 立刻作废

### 2.2 防篡改（替代 TLS 的务实做法）

给每个请求体加 **HMAC-SHA256 签名**：

```
X-TB-Token: <secret>
X-TB-Sign:  HMAC_SHA256(secret, method + path + body + timestamp)
X-TB-Time:  <unix 秒>
```

手机端校验：**签名正确 + 时间戳在 ±300 秒内**（防重放）。
→ 攻击者即使嗅探到请求，也无法**篡改**或**重放**（因为改不动签名、且时间戳会过期）。

### 2.3 数据保护（P1）

- **桌面端**：把 `taskguide.db` 迁到用户私有目录（`%APPDATA%`）并收紧文件 ACL
- **手机端**：依赖 Android 应用沙箱（已足够）；如需更强可后续上 SQLCipher
- **敏感字段**（昵称、备注）可选做字段级加密

### 2.4 上线加固（防逆向 / 防篡改）

| 措施 | 平台 | 说明 |
| --- | --- | --- |
| **正式签名 keystore** | 手机端 | ⚠️ 当前 release **用的是 debug 签名**，必须换 |
| **R8 / ProGuard 混淆** | 手机端 | 开启后类名/方法名被混淆，显著提高破解成本 |
| **资源混淆 + 字符串加密** | 手机端 | 关键字符串（密钥、接口）不裸奔 |
| **Rust 侧 LTO + strip** | 桌面端 | 减小体积、去掉符号表 |
| **完整性自检** | 双端 | 校验自身签名/哈希，被重打包能察觉 |
| **不要在前端存密钥** | 桌面端 | 前端 JS 是明文的，密钥只放 Rust 侧 |

## 三、会员系统设计（含 boss 要求的 5 轮加固）

### 3.1 权益定义（沿用 boss 拍板 + 我补充）

| 权益 | 免费 | 会员 |
| --- | --- | --- |
| 任务数量 | 不限 | 不限 |
| **追踪任务上限** | **1 个** | 不限 |
| **导出 JSON** | ❌ | ✅ |
| **跨端同步** | ❌ | ✅ |
| **桌面挂件** | ❌ | ✅ |

> ⚠️ **架构前提**：「会员一定是服务端判定的」。
> 若只在客户端判断，用户改一下本地库就能白嫖。
> 因此会员系统与「跨端同步」共用同一个后端 —— 这也正是主卖点。

### 3.2 ⭐ 五轮加固迭代设计

| 轮次 | 做法 | 攻击者需要做什么才能破解 |
| --- | --- | --- |
| **v1** | 本地布尔值（`is_vip=true`） | 改一行数据库 |
| **v2** | 本地**签名凭证**：服务端私钥签发，客户端内置公钥验签 | 伪造签名（无解，除非拿到私钥） |
| **v3** | v2 + **设备指纹绑定**（凭证与设备 ID 绑定） | 复制凭证到别的设备无效 |
| **v4** | v3 + **时间戳 + 时钟回拨检测**（凭证有有效期） | 改系统时间会被发现 |
| **v5** | v4 + **关键功能服务端下发**（同步/导出走服务端接口，服务端按会员状态放行） | 必须攻破服务端 —— 这是最终形态 |

**v5 是终局**：只要核心权益依赖服务端，客户端怎么改都没用。

### 3.3 落地节奏（务实）

- **本次**：先把 v1–v4 的**客户端骨架 + 签名校验链路**写好（服务端可先用本地私钥模拟）
- **紧接着**：接入真实后端（Cloudflare Workers 免费额度即可）→ 升到 v5
- 后端同时承担：**跨端同步中转 + 收据校验 + 会员状态发放**

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| P0 | 手机端 API 鉴权 + 配对码校验 | 修 P0-1 / P0-2，双端同步改 |

## 五、审计结论（一句话）

> **当前版本不能直接上架。**
> 手机端 API 全裸（无鉴权 + 监听 0.0.0.0 + 配对不校验），
> 同一 WiFi 下任何人都能读取、清空、篡改用户数据 —— 这是**上线前必须修的 P0**。
> 桌面端本身没有对外暴露端口，风险主要集中在手机端与传输链路。

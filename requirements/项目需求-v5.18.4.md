# 项目需求 v5.18.4（2026-09-20 凌晨）

> 起点是 boss 那句「**为什么每日任务会出现逾期情况？不是零点刷新吗**」。
> v5.18.3 只修了桌面端的显示与手机端的分支判断；**本轮把手机端真正装机验证了**，
> 过程中又挖出 3 个同源问题，一并修完。

## R1 · 每日任务被当成「逾期未完成」→ 每次冷启动都立即提醒

**代码路径**：`TaskBarApp.kt:46` 每次冷启动跑 `ReminderScheduler.rescheduleAll`。

**根因**：每日型任务（`category=daily` / `type=habit|repeat` / `repeat_rule=daily`）的
`due_at` 存的是「每天几点提醒」（如 09:00），**创建后从不推进**（全仓无滚动逻辑）。
拿它比 `now` 永远落在过去 → 走进「已过期未完成 → 立即提醒」分支。

**修**：新增 `isDailyKindForReminder()` + `nextDailyOccurrence()`（只取「时:分」，
折算到今天/明天）；每日型**不走**"已过期立即提醒"分支。

### A/B 真机实测（decision evidence，不是"应该好了"）

同一台手机（V2131A / Android 12）、同一条 `track=pending` 的每日任务（临时造的），
只换 APK，其余步骤完全一致：强停 → 冷启动 → `dumpsys notification`：

| 组 | 版本 | 冷启动后通知 | 排定的提醒 |
| --- | --- | --- | --- |
| A | 旧版（v5.18.2 构建） | **1 条**「TEST-每日提醒复现 / 到点了，去做吧」❌ | 无 |
| B | v5.18.3 | **0 条** ✅ | WorkSpec 触发 = **09-20 09:00:00** ✅ |

A 组那条通知的时间戳是 **00:35** —— 这就是 boss 说的"天天被当逾期"的真身。

## R2 · 同一任务的提醒被重复排队（开几次 App，到点响几次）

**根因**：`schedule()` 用的是 `WorkManager.enqueue()`，而 `rescheduleAll` **每次冷启动**都跑
→ 每开一次 App 就给同一任务**再加一条**同样的提醒。
真机证据：一个任务的 `reminder_<uuid>` 标签下堆了 **20 条** WorkSpec。

**修**：`enqueueUniqueWork(tagFor(uuid), ExistingWorkPolicy.REPLACE, req)`。

**实测**：连续冷启动 3 次，该任务的条目数**稳定不增长**（504→500 分只是延迟随当前时间变短，
每次都是 REPLACE 同一条）。

## R3 · 每日任务「完成过一次」之后，提醒再也不响 ⭐ 最隐蔽

**根因**：`observeMainList()` 的 SQL 自带 **`WHERE track_status != 'done'`**；
而每日任务"昨天已完成"在原始库里**仍然是 done**（每日折算 `normalizeDailyReset`
只发生在 UI 读取层）。于是它在 **SQL 层就被滤掉**，排程逻辑根本看不到它
→ **今天的提醒永远排不上**。全仓又只有 `rescheduleAll` 这一个排程入口。

⚠️ **这条不修的话，R1 修完会变成"提醒彻底不响"** —— 因为旧版那个"冷启动误提醒"
反而一直在替他"提醒"。

**修**：
- `TaskDao.observeRemindable()`：`SELECT * FROM tasks WHERE deleted = 0 AND due_at IS NOT NULL`（**不过滤 track_status**）
- `TaskRepository.observeRemindable()` 转发
- `rescheduleAll` 改用该数据源，并在 Kotlin 侧判断
  `effectivelyDone = DONE && (!dailyKind || doneAt >= 今天0点)`（与 UI 同口径）

**实测**：boss 真实的「健身」（`track=done`、`done_at=09-19 19:38`、`due_at=09-18 09:00`）
→ 冷启动后**被正确排到 09-20 09:00:00（带唯一名）** ✅，且通知栏 0 条。

## R4 · 删掉的任务，到点还会弹一次提醒

**根因**：`observeByUuid` 是 `SELECT * ... LIMIT 1`，**不过滤 deleted**；
而删除任务**不会**取消已排的提醒（删除路径里没有 `cancel`）。

**修**：`ReminderWorker` 补守卫 `if (t.deleted != 0) return Result.success()`。
副作用是历史遗留的"孤儿"提醒条目触发后自动作废。

**实测（决定性）**：把临时任务的提醒改到 150 秒后 → 冷启动排上 → **删掉任务** → 等到点：
- 该 WorkSpec `state=2`（SUCCEEDED）、`run_attempt_count=1` → **确认到点被真正拉起执行过**
- 通知栏 **0 条** ✅（没有守卫的话，这就等于弹一条已删除任务的提醒）

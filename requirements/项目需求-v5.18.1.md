# 项目需求 v5.18.1（2026-09-19 晚）

> 本文含两批：**R1–R5 = v5.18.0**（通知栏改造）、**R6–R7 = v5.18.1**（真机暴露的崩溃与数据一致性修复）。

> boss：「手机端的下滑通知栏里依旧有那个"同步服务运行中" 我不想看到这个
>        只有追踪中的任务可以上去」

## R1 · 通知栏只承载「追踪中的任务」

### 改前
`SyncService` 是前台服务，`onStartCommand` 里无条件 `startForeground()`，
通知固定是「任务指南 / **同步服务运行中**」—— 只要 App 在跑，通知栏就永远挂着它。

### ⚠️ 技术前提（决定了实现方式）
**Android 硬规定：前台服务必须有可见通知，且用户不能划掉。**
所以"后台常驻 + 不显示通知"在 Android 上**只能二选一**。

按 boss 的要求选「不要通知」：
- **有追踪任务** → 前台服务 + 通知（通知内容就是任务本身）
- **无追踪任务** → `stopForeground(STOP_FOREGROUND_REMOVE)` 撤掉通知；
  服务本身**继续作为普通后台服务**提供同步

### 通知内容（boss R30 的原话：名字挂上面，有步骤就下面小字写）
| 位置 | 内容 |
| --- | --- |
| 标题 | 任务名 |
| 正文（小字） | `2/5 · 洗菜`（当前步骤 + 序号）—— 没有步骤就不显示 |
| 右下角 | `共 N 个追踪中`（仅当追踪多于 1 个） |
| 点击 | 打开 App（SINGLE_TOP + CLEAR_TOP） |
| 属性 | ongoing（划不掉）+ silent（不响不震）+ onlyAlertOnce |

### 通道
沿用原通道 id `ch_service`，但**名称由「同步服务」改为「任务追踪」**、描述改为「显示正在追踪的任务」。
⚠️ 通道原来用 `getNotificationChannel()==null` 守卫 —— 老装机上通道已存在，
名字永远改不过来；改为**每次都创建一次**（系统只允许更新名称/描述，不会重置用户的开关与重要性）。

## R2 · 追踪状态变化的触发方式

**不在**"开始/停止追踪"的各个入口逐个埋点，而是订阅一个 Flow：

```kotlin
repo.observeTrackingFeed()   // combine(taskDao.observeTracking(), stepDao.observeAll())
    .collect { SyncService.refreshTracking(it) }
```

理由：订阅式能覆盖**所有**来源的变化 —— 手动开始/停止、步骤推进、打卡解除追踪、
以及**电脑端同步过来的改动**（逐个埋点必然漏掉同步这条路径）。

正文写的是"当前步骤"，所以步骤 Flow 也必须一起订阅。

## R3 · 刷新走同进程直调，不走 startService

`SyncService.instance`（同进程静态引用）+ `mainHandler.post{}` 直接更新通知。
理由：Android 12+ 禁止 App 在后台 startService/startForegroundService，
走 IPC 会静默失败；同进程直调没有任何限制。

## R4 · 系统重启服务的兜底（START_STICKY）
`onStartCommand(intent == null)` 时拿不到追踪状态，处理顺序：
1. 先用 `lastInfo`（上次已知状态）——避免通知先弹占位再撤掉来回跳
2. 异步查一次库补正（`refreshFromDb()`）
3. 若确实没有追踪任务，仍要先 `handshake` 过一下桥：
   `Context.startForegroundService()` 启的服务**必须在 5 秒内调用一次 `startForeground()`**，
   否则抛 `RemoteServiceException` 直接把进程干掉。过桥用一条极简通知，随即 `stopForeground(REMOVE)`。

## R5 · 顺带修：src 里的 SyncService.kt 本身编译不过
覆盖编译副本后报 `Unresolved reference: ConnectivityManager`。
查明：`src/.../SyncService.kt` **缺 `android.net.ConnectivityManager` 与 `android.net.Network` 两个 import**
（历史上有人在编译副本里补过、没有同步回源，所以一直没暴露）。已补进源文件。

## ⚠️ 代价（如实记录）
前台态一撤，Android 会把服务降级为"普通后台服务"，**可能被系统/厂商省电策略回收**。
后果：手机 App 长时间在后台时，桌面端可能连不上手机。

**但不会丢数据**：桌面端有自己的本地库，离线期间的改动都存在本地；
等手机 App 再打开（服务重启）时会走 `full_sync` + `push_full` 按 `updated_at` 做 LWW 合并补上，
表现为「**同步延迟**」而不是「数据丢失」。

若要"后台常驻 + 可接收同步"，只能把通知放回来 —— 取舍权在 boss。
后续可配合 **OemCompat（厂商自启动/电池白名单引导）** 提高存活率。

## R6 · ⚠️ 真机第一次安装就崩溃（已修）：`ForegroundServiceDidNotStartInTimeException`

### 现象
装上新版后 App 一起来就死，进程直接消失（8899 不通、通知栏倒是"干净"了 ——
但那是**服务根本没起来**的假象）。crash.log：

```
android.app.ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground():
ServiceRecord{... com.taskbar.app/.server.SyncService}
```

### 根因（我第一版的逻辑错）
我把"要不要过桥"绑在了**知不知道追踪状态**上：
- `start()` 路径（MainActivity / BootReceiver）：`handshake = false`
- 于是"无追踪任务"时直接走 `stopForeground(REMOVE)`，**一次 `startForeground()` 都没调用过**

而 Android 的硬规定是：**只要这个服务是用 `Context.startForegroundService()` 启动的，
就必须在 5 秒内调用过一次 `startForeground()`**，与"有没有追踪任务"无关。
（这一条我在需求文档 R1 备注里写过，却在实现里绑错了条件 —— 写完不等于做对。）

### 修法：把条件解耦成"启动方式"
参数从 `handshake` 改名为 `mustForeground`，语义 = **本次 onStartCommand 是否来自
`startForegroundService()` 启动的 intent**：
| 路径 | mustForeground | 理由 |
| --- | --- | --- |
| `start()` 带 extras（MainActivity） | **true** | startForegroundService 启动 |
| `start()` 无 extras（系统重启服务） | **true** | 同上，保守取值 |
| `refreshTracking()` 同进程直调 | false | 不是服务启动，没有 5 秒义务 |

无追踪时的顺序固定为：**先 `promote(极简通知)` 过桥 → 再 `stopForeground(REMOVE)`**。
并引入 `bridged` 局部变量，避免"过桥后忘了撤"（否则那条占位通知会永远挂着）。

### 复验（真机）
重装后：进程存活 ✅ / 8899 可达 ✅ / crash.log 无新条目 ✅ / 通知栏 0 条 ✅

## R7 · 真机验证时顺带挖出的数据一致性 bug（已修）：孤儿步骤

### 现象
从电脑端删除那条临时任务后：桌面端 steps 全部 `deleted=1`，
**手机端那条步骤仍是 `deleted=0`** —— 任务没了，步骤还在。

### 根因：双端**发送端**都漏推步骤的删除
| 端 | 本地动作 | 实际推送 |
| --- | --- | --- |
| 手机端 `deleteTask` | 软删任务 + 软删关联步骤 | 只 emit `("delete","task")` |
| 桌面端 `delete_task` | 软删任务 + 软删关联步骤 | 只 `push_change("task")` |

而两端 `applyChange` **都支持** `("delete","step")` —— 所以是纯粹的漏推。
后果：删除只靠"下一次全量同步"（每次 WS 重连都会做 `push_full`，含已删除行）覆盖，
窗口期内两库不一致。界面上看不见（步骤按 `task_uuid` 查，父任务已删），
但数据在污染，且这类"看不见的不一致"最容易在以后变成玄学 bug。

### 修法（三层）
1. **两端发送端**：逐条推步骤的 `delete`
2. **两端接收端**：`("delete","task")` 时**级联**软删该任务的步骤（兜底老版本对端）
3. **桌面端 `push_change` 失败留痕**：原来 `let _ =` 把结果全吞了，
   "这条变更到底推没推过去"完全不可观测 —— 排查步骤同步时正是被它挡住了视线。
   现在区分 `Ok((true,_))` / `Ok((false,msg))` / `Err(e)` 三种情况分别 warn。

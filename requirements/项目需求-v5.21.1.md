### ⚠️ 测试方法上踩到的两个坑（重要）

**坑 1：拿"末位字符"当篡改样本 = 白测。**
`base64url` 的 94 字符签名段 = `4*23+2` → 末 2 字符只剩 8 位有效，**4 位被丢弃**。
改末位字符解码后**签名完全一样**，所以「被接受」是**正确行为**，不是漏洞。
→ **以后做篡改测试必须改中间字符**（本次改签名段第 9 位，成功触发拒绝）。

**坑 2：`adb shell input text` 会被中文输入法"猜词"吃掉。**
本机默认输入法 Sogou（和 Baidu 输入法），注入字母串时被当拼音转成汉字
（例：`VEIxfHBy...` → `VEI媳妇HB要不3我也...`），**139 字符的授权码根本输不进去**。
→ 解法：`adb shell ime disable <id>` 把输入法全关掉，按键直接进输入框，字符原样落地；
   验完**立刻 `ime enable` + `ime set` 还原**（本次已还原：Sogou 已启用并设为默认）。

### 另注（安全面观察，非缺陷）
授权状态是明文 prefs（`license_code` + `license_tier`）。root 用户可手改 `license_tier` 伪造成 pro。
对 ¥5 买断的 App 不值得加壳对抗；真要加固再说。**安全性主体仍由 ECDSA 决定**（知道公钥造不出签名）。

## R2 · 提醒：系统闹钟端到端实响验证（v5.18.5 的缺口，本次补齐）

v5.18.5 把提醒从 WorkManager 换成系统精确闹钟，但"到点真响那一下"一直没验成。本次补上：

**方法**：从桌面端造一条 **4 分钟后到点**的任务（`dueAt = now+4min`）→ 同步到手机 → 冷启动 App 触发重排 → 查闹钟 → 等到点 → 查通知。

| 观察点 | 结果 |
| --- | --- |
| `dumpsys alarm` 排上的闹钟 | ✅ **2 条**：`09-22 00:14:00`（测试任务）、`09-22 09:00:00`（健身） |
| 到点后通知栏 | ✅ `TEST-闹钟实响` / `到点了，去做吧`，**弹出时刻 = 09-22 00:14:00（精确到秒）** |
| 闹钟是否被消耗 | ✅ 剩 1 条（`09:00:00` 那条），00:14 那条已消耗 |
| WorkManager 兜底（测试任务） | 也执行了 1 次（当时屏幕亮着、App 刚启动） |
| WorkManager 兜底（健身） | ❌ 仍 `state=0 执行 0 次` —— **夜里设备休眠时它就是不跑**（与之前的结论一致） |

**结论**：闹钟机制在**到点那一刻精确触发**，且是唯一在设备休眠场景下可依赖的路径。
⚠️ 严格说：本次两条路径（闹钟 + 兜底）同时具备触发条件，无法 100% 归因到闹钟；
但健身那条兜底"计划 09:00、执行 0 次"的历史 + 本次闹钟精确到秒，足以支撑机制可用。

## 已定位真根因（代码级，3 条）

### R1 · 自动扫描只在两个时机跑，跑完就永不重试 【主因】

- `app3.js:2733` 启动后 3s 调 `autoScanAndReconnect(2)` → 只扫 **2 轮×2.5s = 5s** 就结束
- `app3.js:1967` 打开设置页时调 `autoScanAndReconnect(3)` → 只扫 **3 轮 = 7.5s** 就结束

**问题**：这两个时机之外完全没有扫描。所以下面这些场景**一次扫描机会都没有**：
- 启动时手机还没连上 WiFi（最常见 —— 电脑先开机，手机后连 WiFi）
- 电脑中途断网再恢复
- 手机 WiFi 重连 / 息屏后再唤醒

→ 正是 boss 遇到的全部场景。`autoScanAndReconnect` 跑完那几轮后就**彻底停手**，
只剩 Rust 侧兜底，而 Rust 侧又慢（见 R2）。

### R2 · Rust 侧 mDNS 重发现窗口太短 + 轮询太慢 【放大器】

- `lib.rs:1620` 每轮 mDNS 扫描窗口只有 **4 秒**
- 失败后 `continue` → 下一轮要等 `sleep 5s` + `ping 超时 3s` = **8 秒**才有下一次扫描机会
- Android NSD（`MdnsRegistrar`）注册/广播本身有 1~5s 延迟

**问题**：手机刚连上 WiFi 时，那 4 秒窗口极容易空手而归；连续几轮都扫不到 →
桌面端持续「连不上」→ 前端持续弹「配对手机不在网络」。

### R3 · 前端提示在误导用户手动操作 【boss 直接看到的现象】

- `app3.js:279` 状态文案：`已配对（缓存）· 当前未连接 — 点击下方"扫描设备"重连`
- `app3.js:2813` toast：`⚠ 配对手机不在网络，正在后台自动重连…`

**问题**：文案明确指示「点击扫描设备」，用户看到自然就以为**必须手点**。
而实际上后台扫描时机根本不存在（R1）—— 点一下反而真连上了，
于是形成「只能手动点」的错误认知。

## 修法

### 前端（`ui/app3.js`）

| 改动 | 内容 |
| --- | --- |
| **新增常驻看门狗** | `startAutoScanWatchdog()`：`setInterval(autoScanWatchdog, 5000)` + 启动立即查一次。只要「已配对 && 未连接」就调 `autoScanAndReconnect(1)`，连上即静默停手 |
| **rounds 语义放宽** | `rounds <= 0` = 无限重试（原只支持有限轮） |
| **优先 deviceId 匹配** | 发现列表里优先选 `deviceId === settings.pairing.deviceId` 的（手机换 IP 也能连回原配对） |
| **文案修正** | 状态 → `已配对（缓存）· 当前未连接 — 正在自动扫描重连…`；toast → `⚠ 手机暂时不在网络，正在自动扫描重连…`（间隔 30s→60s） |

### Rust（`src/lib.rs` · `auto_reconnect_loop`）

| 改动 | 内容 |
| --- | --- |
| **扫描窗口自适应** | `fail_count >= 8 → 12s`｜`>= 3 → 8s`｜否则 `4s`（失败越多扫越久） |
| **轮询间隔自适应** | 断连期 `5s → 2s`（连上后回落 5s 省电） |
| **ping 超时自适应** | `fail_count >= 3` 时 `3000ms → 1500ms`（目标 IP 已失效时不用干等 3s） |

**效果对比**（最坏情况：手机刚连上 WiFi、IP 已变）

| | 旧 | 新 |
| --- | --- | --- |
| 首次扫描机会 | 启动后 3s，之后**永久没有** | 启动即查 + 每 5s 持续检查 |
| 单轮扫描窗口 | 4s | 4s → 8s → 12s 自适应 |
| 重试周期 | 8s（且前端不参与） | 2s（前端 5s 常驻 + Rust 2s 兜底） |
| 预估发现耗时 | **永远发现不了**（除手动点） | **≤ 10s** |

### 待 boss 实测的判定方法

1. 手机打开「任务栏」→ 设置 → 确认同步服务器在跑（可与电脑不同步地先断一次 WiFi 再连）
2. 电脑双击 **`D:\Desktop\任务栏-调试模式.cmd`**
3. 观察设置页「配对状态」：应在 **≤10 秒**内从「正在自动扫描重连…」变成「已配对 · 实时连接中：http://…」
4. 若一直不连上 → 说明 mDNS 组播被路由器/防火墙挡了（部分路由器默认关闭 IGMP/组播转发），
   此时**手动点一次「扫描设备」**仍应成功；若手动也扫不到，则问题在手机端未广播（`MdnsRegistrar` 被多播锁拒绝）

### 已知限制（如实说明）

- 自动扫描依赖 **mDNS/组播**。少数路由器（尤其企业网 / 开了 AP 隔离）会拦组播 →
  两端即使同一 WiFi 也发现不了。此为网络环境问题，非代码缺陷；`10.200.37.x` 这种网段
  通常是校园网/企业网，组播被拦的概率不低。若实测失败，**首选方案是给手机设固定 IP**
  或改用「按上次 IP + mDNS 双路尝试」策略 —— 待 boss 反馈后决定。
